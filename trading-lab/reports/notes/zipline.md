# zipline-reloaded (3.2.1) engine accuracy notes

Adapters: `adapters/zipline_S2.py` (daily, ~10 s), `adapters/zipline_S1.py` (minute mode, ~2.5 min). Python: envs/zipline (3.11).
Packages: nothing installed (pyarrow not needed; `lab.data` imports fine). Bundles are written to a fresh temp dir under /tmp (`ZIPLINE_ROOT`), nothing in the repo.
All 30 DOW symbols run in ONE algorithm per strategy. Entries, exits, share counts, fill prices come from zipline's blotter/transactions (`result.transactions`).
`pnl_net`: zipline's transaction records have no per-trade net P&L, so pnl_net = (exit-entry)*shares - 0.0005*(entry+exit)*shares from the engine's fill prices/shares (the same PerDollar(0.0005) formula the engine charged). Cross-check: the sum equals the engine's own `portfolio_value[-1]-capital` (S2 54050.1468 vs 54050.1468; S1 -83953.18429 vs -83953.18429).

## Problems and causes
1. Data bundle. Custom `bundles.register(name, ingest, calendar_name=..., start_session, end_session)` with an in-memory ingest function (asset_db_writer / daily_bar_writer / minute_bar_writer fed from `lab.data`). Equity metadata `start_date/end_date/auto_close_date` per symbol. Two symbols-groups: 521-day symbols end 2025-08-27, others 2025-12-31 (no problem). Calendar: S2 uses XNYS (608 sessions = our 608 days exactly).
2. Fill price is the CLOSE by default. `zipline/finance/slippage.py`: `SlippageModel.simulate()` uses `data.current(asset,"close")` and `NoSlippage.process_order`, `FixedSlippage`, `VolumeShareSlippage`, `FixedBasisPointsSlippage` all fill at `data.current(order.asset,"close")` (lines ~169, 224, 313, 363, 667). In daily mode an order placed in `handle_data` on day t is processed at the start of the day-t+1 bar (`gens/tradesimulation.py::every_bar` calls `blotter.get_transactions` before `handle_data`) and `data.current` is day t+1's bar, so default = day t+1 CLOSE. No built-in setting fills at the open.
   Fix: user-defined slippage model (documented extension point, subclass of `EquitySlippageModel`, `set_slippage(us_equities=...)`) whose `process_order` returns `data.current(asset,"open")`. Slippage is therefore zero; commission = `commission.PerDollar(cost=0.0005)` (`commission.py::PerDollar.calculate` = |amount|*price*cost).
3. Sizing floor(10000/next open) is unknown at order time (`order_value`/`order_target_value` size from the previous close). Fix: the order is placed with an oversized amount (10**9, only an upper bound) and the same custom fill model returns `min(floor(10000/open), open_amount)` shares (the fill model decides the executed volume: that is how zipline expresses partial fills; `slippage.py::process_order` contract). The unfilled remainder stays open, so `handle_data` cancels open buy orders at the next bar (`cancel_order`). Sells order exactly the held amount. Share counts, prices and cost come from the engine's transactions; no sizing mismatch (0). Note: this puts the sizing rule inside the fill model; without this trick the sizing would use the previous close and differ on most trades.
4. S2 rule 4 (close open positions at last day's close) is impossible natively: orders fill at the next bar, and `run_algorithm` ends at the last session (no auto-liquidation). Workaround (data-side, same as backtesting.py adapter): per symbol append one synthetic session (next XNYS session after its last real day; O=H=L=C= last real close, volume 1; volume 0 would be skipped by `SlippageModel.simulate`). On the last real day the strategy sells; the engine fills it at the synthetic bar's OPEN (= last close). Exit time is mapped back to the last real date in post-processing. The strategy places no entries on the last real day. Affects 21 symbols with an open trade (earlier engines had 21 such exits).
5. S1 / 1-minute only. zipline's minute store (`data/bcolz_minute_bars.py`) has one slot per calendar minute (390/day, labels = minute END, first minute 09:31 ET). It cannot hold a 5-minute bar natively. Device: each 5-min bar (O,H,L,C,V unchanged) is written into the single 1-min slot labelled start+1min (09:31 for the 09:30 bar); the other 4 minutes are empty (volume 0). `SlippageModel.simulate` returns immediately when `volume == 0`, so an order placed when bar k is visible fills at the next minute with data = bar k+1, at its open. `handle_data` returns unless (dt-1min).minute % 5 == 0. This is a data-mapping device, not native 5-min support; zipline performs the fills. First attempt wrote at start (09:30) and lost the first bar of every day (09:30 is not a calendar minute): 10708 trades vs 9304.
6. Price precision. `bundles/core.py` builds the `BcolzMinuteBarWriter` with default `ohlc_ratio=1000`, i.e. prices stored as uint32 round(p*1000); our 5-min prices have 4 decimals (e.g. 191.7901) so entry prices differed by up to 5e-4 on 777 trades. Fix: in `ingest` build a `BcolzMinuteBarWriter(..., default_ohlc_ratio=10000)` on the same rootdir (the class accepts it; the bundle machinery just does not pass it). Result: 0 price mismatches. (Daily bar writer has the same 1000 scaling, irrelevant for S2/prices have 2 decimals there, and daily data is not used for fills in S1.)
7. Early-close days. The lab's 5-min data has full 78-bar days (to 15:55) on NYSE early-close days (2023-11-24, 2024-07-03, 2024-11-29, 2024-12-24, 2025-07-03, 2025-11-28, 2025-12-24 and similar, volume looks synthetic e.g. 1000). XNYS closes 13:00 on those days, so the bar writer drops all minutes after 13:00 and positions could not exit at 15:55 (5 missing/1 extra trade, 8 exit mismatches, max pnl diff $276). Fix: registered calendar `XNYS_FULLDAYS` = `XNYSExchangeCalendar` subclass with `special_closes`/`special_closes_adhoc` empty (full 09:30-16:00 sessions on those days). This changes the calendar to fit the data (the data, not the exchange, says those days were full), documented here.
8. S1 protocol reading: rule 3 exit check on every bar up to 15:45 while long, entries only 10:00-15:40, rule 4 sell order at the 15:50 bar (fills 15:55). Range and day-valid flags (>=78 bars) per day: validity set from pandas counts, range high/low accumulated in `handle_data` from engine bar data.
9. Misc: benchmark must be supplied (`benchmark_returns=zeros`) to avoid a network fetch; `set_cancel_policy(NeverCancel)` so orders are not cancelled at session end; the bundle calendar object must be the one from `zipline.utils.calendar_utils.get_calendar` (using `exchange_calendars.get_calendar` directly raised "All readers must share target trading_calendar").
